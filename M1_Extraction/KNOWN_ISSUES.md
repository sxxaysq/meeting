# 回归结果与已知错误案例

模型：`Qwen/Qwen3.6-35B-A3B`（192.168.30.215:8000，vLLM，`enable_thinking=false`）
数据：10 份周例会 PDF 全量，对照 `items.annotation_v3.merge_group.json` 共 1367 条人工标注。

复现：

```bash
python eval/batch_regression.py --pdf-dir /home/yty/数据集/原始数据 --annotation /home/yty/标注/items.annotation_v3.merge_group.json --out-dir out_v2 --workers 6
```

## 1. `item_type`：主要分歧是标注把大量列举内容判为 NON_TASK_ITEM

混淆分布（gold → pred）：

| gold | pred | 条数 |
|------|------|------|
| `NON_TASK_ITEM` | `NON_PROJECT_WORK` | 86 |
| `NON_TASK_ITEM` | `PROJECT_TASK` | 77 |
| `PROJECT_TASK` | `NON_PROJECT_WORK` | 67 |
| `RESEARCH_TASK` | `NON_PROJECT_WORK` | 35 |

前两行合计 163 条，全部是"采购管理""招采清单"这类**台账式列举**。
人工标注认为它们只是信息列举、不构成任务；M1 认为每条都有明确执行动作。
例如"红沙泉项目人员定位及运输管控系统采购"，标注是
`NON_TASK_ITEM` + `project=null`，M1 给 `PROJECT_TASK` + 项目名。

**这是标注口径分歧，不是模型臆造**——原文确实写了项目名和采购动作。
按需求"不要修改标注数据来迎合模型输出"，此处保留差异。
若业务上确认招采台账不应进入任务流，正确做法是在
`prompts/item_extractor.md` 的 `NON_TASK_ITEM` 定义里补一条
"招采清单/台账式列举不算任务"，而不是改标注。

后两行是模型判断偏保守，已通过提示词补充判据缓解
（"有项目归属就是 PROJECT_TASK，不因动作像日常事务而降级"、
"科研板块/课题/专利类即使无项目名也判 RESEARCH_TASK"），
item_type 从 0.750 提升到 0.760，但没有根治。

## 2. `project`：0.659，四类差异

| 类型 | 条数 |
|------|------|
| 两边都有但不同 | 175 |
| 标注留空 / M1 给了项目名 | 102 |
| 标注有 / M1 留空 | 57 |
| 包含关系（粒度差，如 `红沙泉项目` vs `红沙泉二矿项目`） | 56 |

第二类基本就是上一节的招采台账。**M1 侧没有臆造**：
质量门的 `PROJECT_NOT_IN_SOURCE` 在全量 10 份文档上是 **0 命中**。

### 已修复：模型会拼接项目名

早期版本有 19 条 `PROJECT_NOT_IN_SOURCE`，全部是**拼接**：

| 原文 | 模型输出（错） | 正确 |
|------|--------------|------|
| `4.天地奔牛一是ERP 项目：…二是SCM 项目：…` | `天地奔牛ERP项目` | `ERP 项目` |
| `针对小纪汗34 条专家意见，完成初设文件修改` | `小纪汗项目` | `null` |
| `太原院：MOM 二期…` | `太原院MOM 二期` | `MOM 二期` |

单位名属于 `delivery_group`，不属于 `project`；给没有"项目"二字的名称加后缀也是归一。
两处修复：提示词加了三条禁令 + 示例；`item_extractor._check_project`
增加确定性护栏——`project` 必须是原文的连续片段（忽略空白），
不是就置空并写入 `normalize_warnings`，不静默编造。
全量运行中该护栏只触发 8 次，全部命中真实拼接，无误伤。

## 3. `work_section`：0.287 主要是标注产物

* "下一步工作要求"章节里，标注把**整句话**写进了 `work_section`
  （例："安全生产部会同数字咨询规划研究院要在西安展会布展期间…"），M1 输出 `null`。
* 职能部门（人力资源部、纪检专干等）直接在部门下列条目、没有板块小标题时，
  标注同样把条目正文填进了 `work_section`。

因此评测额外报告"真实板块名子集"（标注值长度 ≤ 20），为 0.591。

已修复的真实 bug：`1.集团总部及子企业一.售前项目跟进：` 这类
"板块名 + 行尾粘连子标题"的行，早期实现只取前半段（单份文档即占 26 处不一致）。

## 4. 粒度：总数接近不等于逐条对齐

1444 vs 1367（1.056）看起来吻合，但严格配对只有 1142 对。两种偏差相抵：

* 标注把一个项目下的 ①②③ 合成**一条**（红沙泉二矿项目 9 个子系统 → 1 条），
  M1 按需求"宁可拆多"拆成 9 条；
* 招采清单等则相反。

按需求第八节 M1 取向是**优先拆分**、由 M2 归并，所以拆细不算错误。
评测因此以 `coverage`（标注区间被预测区间覆盖 ≥ 90%）为召回口径，为 0.950。

## 5. 单次运行存在方差

`temperature=0`，但 vLLM 并发下不完全确定。同一份文档两次运行
coverage 可在 0.85–0.99 之间波动（如 04-20 两次分别为 0.988 / 0.856）。
**单次跑分不要当作精确指标**，比较提示词改动时应多跑几次或固定并发为 1。

## 6. 已修复：条目密集的 Block 会被输出截断

`（1）…（26）` 这类一个 Block 26 条的段落，一次要产出 26 个 Item，
`max_tokens=4096` 会把 JSON 截断，repair 也救不回来，整块作废
（04-13 因此 coverage 只有 0.774）。默认值提高到 8192 后该文档回到 0.976，
全量截断数为 0。`LLMClient` 现在会统计 `truncations`，不再无声失败。

## 7. 已修复：单个字段不合法不再赔上整条 Item

模型偶尔把单位名写进 `assignee`（如 `["人力资源部","数字咨询规划研究院"]`）。
早期实现丢弃整条 Item，损失召回。现在只清空该字段并写入
`normalize_warnings`，Item 保留——这不是静默修正，告警会进 report。

## 8. 环境限制

* **Ollama(7060) 的 OpenAI 兼容层把上下文硬截断到 4096 token**
  （实测 9000 token 输入的 `prompt_tokens` 仍是 4096）。
  用 Ollama 时必须 `LLM_TRANSPORT=ollama` 走原生 `/api/chat` + `num_ctx`。
  215 的 vLLM 无此问题（`max_model_len=262144`），已作为默认。
* **思考型模型必须关思考**。Qwen3.x 默认把推理写进独立的 `reasoning` 字段，
  `content` 直接是 `null`，不关的话解析必然失败。
  已由 `LLM_ENABLE_THINKING=false` 处理（发送 `chat_template_kwargs`），
  并保留从 `reasoning` 兜底取 JSON 的路径与计数。
* Dify 的 Document Extractor 不返回分页信息，Dify 链路上
  `page_start/page_end` 恒为 `null`；CLI 链路有真实页码。
* 模型对比：Ollama qwen3:30b 单份约 10 分钟，215 的 36B-A3B 约 26 秒（约 23 倍）。

## 10. generic 提示词第 9 条（圈码子条目）的由来

`prompts/generic_item_extractor.md` 新增第 9 条：

> 9. 原文用圈码 ①②③ 标出的条目，每一条都要单独抽一条，**尤其不要跳过开头的 ①②**，这是漏抽最常见的位置。这一条只影响有没有抽到，不改变任何其他判断：拆分粒度仍按第 2、3 条，不要把同一行原文拆成多条；project 仍按第 6 条，判断不出来就填 null，不要因为条目排在某个标题下面就给它套一个项目名。

起因：generic 会把项目名后面紧跟的 ①② 子条目整段跳过。
0407 的 `[380,484]`（①集控中心 / ②数据中心）一条没抽到，block 模式两条都在。

全量对比（各 1 次运行，`out_generic_v4` 是保留版）：

| 指标 | 改前 | v2宽 | v3窄 | **v4** |
|---|---|---|---|---|
| coverage | 0.9261 | 0.9239 | 0.9429 | 0.9312 |
| exact_match | 0.983 | 0.9865 | 0.9916 | 0.9885 |
| project | 0.4793 | 0.4385 | 0.3828 | **0.5672** |
| item_type | 0.8133 | 0.8029 | 0.7958 | 0.8157 |
| department | 0.9731 | 0.9711 | 0.9461 | 0.9519 |
| 质量门 error | 100 | 140 | 133 | 116 |

v4 在 5 项上优于基线，只有 department 掉 2.1 点、error 涨 16。
project +8.8 点来自 null 判断变准：`project=null` 占比 24.1% → 31.2%（标注是 52.2%）。

**三个不要重犯的写法**（被淘汰的三版输出已归档在
`/home/yty/m1x/_archive_m1_generic_prompt_iters_20260818.tar.gz`，内含各版规则原文）：

1. 规则里带上「1.2.3.、一、二、」→ 模型开始拆**同一行原文**，07-13 从 136 条炸到 207 条，
   两条 item 共用同一 span，evidence 定位失败。
2. 写「**项目名**或小标题后面紧跟」→ 模型把所有条目往上游项目标题挂，
   `project=null` 直接归零，一致率跌到 0.3828。
3. 拿**单份文档**判断改动好坏 → 逐份 coverage 有 ±13 点噪声。
   0407 上看 v4 的 project 是 0.5224（低于基线 0.5522），全量却是 +8.8 点，结论完全相反。

**待办**：v4 只跑了一次，落地前应同配置再跑 2 次看中位数（约 30 分钟）。
